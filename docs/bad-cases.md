# Bad Cases

> 这份文档记录的是**真实发生过**的问题 —— 每一条都能指到具体的页面原话、源码位置或复现步骤。
>
> ★ **一条红线：禁止把「理论风险」写成 Bad Case。**
> 「我觉得这里可能会出问题」不是 Bad Case，「我跑了一遍，它真的这么错了」才是。
> 没有证据的只能进 [`evaluation.md`](./evaluation.md) 的能力边界一节。
>
> **宁可这份文档短，也不要它虚。**
>
> 完整的方法论（四层验收、严重度判据、怎么记录一次失败）见
> [`evaluation.md`](./evaluation.md) 第一节。

---

## 为什么只留这五条

开发和验收过程中真实记录下来的问题有二十多条。这里挑出五条，标准只有一个：
**对做产品的人有参考价值。**

**没有收进来的那些，以及理由**：

- 同一种形状的重复（比如另一条「值相等」的断言分不出算出来的还是手抄的）—— 留一条就够；
- 「只有写检查的人才会遇到的坑」—— 对做产品的人没有参考价值；
- 主题重叠的、结论偏弱的（比如「只记录不修」且影响很轻的）、
  文档自己就声明「刻意不写成缺陷」的；
- 未能复现、未能定性的观察 —— 按上面的红线，它们不是 Bad Case，只是在能力边界里记了一笔。

## 一、决定「屏幕上显示哪一句话」的条件，被简化之后所有检查都还是绿的

### 问题

AI 助手页在换时间窗口时，会显示一条横幅解释「按钮为什么动了、但结果还是旧窗口的」。
这条横幅有**两种措辞**：

- 用户**自己**拨的按钮 → 「**你把**时间窗口切成了…」
- 模型申报后**替他**拨的 → 「**模型把**时间窗口理解成了…」

选哪一条，靠一个内联的三条件表达式判断。**它一条断言都没有。**

### 现象

把那个条件简化成只剩第一个条件之后，页面对**用户自己拨的**那一半，
会开始说「**模型**把时间窗口理解成了…，按钮已经替你拨过去了」。

**一句彻底的假话，而且它看着完全合理。**

而当时**本机那一整套自动化检查全部是绿的**。

### 原因

条件写成了内联表达式 `a && b && c`。

这种形状有两个特点，合起来才构成危险：

1. 它读起来像是有冗余 —— 后人看到会想「后面两个条件不是多余的吗」；
2. 它**内联在渲染逻辑里**，没有任何一条断言看得见它。

于是「简化掉它」这个动作，**在检查上是完全无声的**。

### 产品判断

这不是「少一个数」，是**页面主动告诉用户一件假的事**，严重度高。

★ 但比这一条本身更值钱的，是它带出来的一条通则：

> **凡是决定「显示哪一句」的条件，都要能被单独钉住。**

因为这类条件的失败形态非常特殊：它不报错、不抛异常，
产出的仍然是一句**通顺、合理、看起来对**的话 —— 只是这句话描述的事情没有发生。

### 修改

照这个文件里已有的写法（同一个文件里另有一条横幅本来就是这么做的）：
**把它提成导出的纯函数**，参数是三个值（模型申报的天数、当前按钮的天数、这一轮实际跑的天数），
返回「这句横幅该由谁来说」。

然后**钉它的真值表**：1 种返回 true 的情形 + 7 种返回 false 的情形，逐条验。
每一种漏掉，都会让页面在某个场景下说假话。

### 验证结果

反证：把它改回简化版，确认**旧断言全绿、新断言红** —— 这正是要证明的那件事：
旧的那批检查确实看不见它。改回正确版本后全绿。

## 二、中间那层代理回的错，被说成「后端回应了 502」

### 问题

用户在本机起了后端，打开 AI 助手页，页面却显示：

> 本机后端回应了 HTTP 502，不是预期的 200。

### 现象

**这句话是假的。**

查下来：那个端口上**根本没有任何进程在监听**；而后端源码全文件**没有一处返回 502**
（它只回 200 / 204 / 403 / 404 / 429 / 500 / 503）。

那个 502 是**开发服务器的转发器**发的 —— 它转发不到后端时，替后端写了一个空 body 的 502。

### 原因

把「拿到一个非 200 的响应」直接翻译成了「后端回的错」，
**没有区分这个响应是谁回的**。

### 产品判断

严重度高，但**危险的方向和直觉相反**：

这句话会让用户去**排查一个根本没坏的东西**（后端是不是出错了、是不是版本不对），
而真正该做的事 —— 把那个窗口打开 —— 他反而不会做。

★ 由此得到一条可以当通则用的判据：

> **本机后端的应答永远是 JSON，成功和失败都是。**
> 所以**任何一次「拿到的不是 JSON」，都说明这层应答不是它发的。**

按这个判据，「拿到一个非 JSON 的 502」应该翻译成
「**本机后端连不上 —— 多半是它还没有启动**」。

### 修改

三个入口（启动探测 / 提问失败 / Python 调用失败）**共用同一句真话**，
并且**已经起过后端的人会看到下一步该做什么**。

### 验证结果

两处独立的检查各自钉了这条回归，并且**两处都额外钉了反方向的那一条**：

> 最危险的失败形状是**反过来的过度泛化** ——
> 把「后端答了个错（403 / 503）」也说成「后端不在」，
> 用户就会去重启一个根本没坏的东西。

所以正反两个方向都必须有断言，只钉一边是不够的。

## 三、一条消息里的每一条工具调用，都必须紧跟一条回复

### 问题

模型一次响应里返回了**多条**工具调用，代码「执行一半就跳出」，
导致这一批剩下的调用**永远等不到回复**；下一次请求被后端直接拒绝。

### 现象

**多轮对话的第二问必崩。** 后端返回 400，原话是：

```
An assistant message with 'tool_calls' must be followed by tool messages
responding to each 'tool_call_id'.
(insufficient tool messages following tool_calls message)
```

### 原因

两条路上**各有一个提前跳出**：工具预算用完时跳出、检测到连续重复调用时跳出。

★ 值得注意的是：**「先把整条助手消息推进消息数组、再逐条执行」这个顺序本身没错**，
错的是「逐条执行时**中途**跳出」—— 一跳出，后面那几条调用就永远等不到回复。

★ **同源缺陷有两处，不是一处。** 只修预算那一条路，同一条错误会换条路再来一遍。
找这类缺陷的正确问法是「**还有没有别的地方会提前跳出这一批**」，
而不是「这个分支修好了吗」。

### 产品判断

严重度高 —— 多轮对话直接不能用，而多轮对话正是这一版要做的事。

★★ **但这条真正值得记的地方在于它为什么躲过了当时那一整套自动化检查** ——
而那些检查**一条都没红**：

> 所有测试场景里的工具调用，要么只有一条、要么两条且都装得下。
> 「已经累积到上限时还要调工具」这条分支，**从来没有被执行过一次**。

**不是检查错了，是那一块压根没被看过。**

带来的一条通用教训：**「全绿」只能证明「检查覆盖到的地方是对的」**，
它证明不了「检查覆盖到了该覆盖的地方」。

### 修改

改成**一批要么整批执行、要么整批拒绝，绝不执行一半**。

由此得到一个**可证明的硬上限**：上一批结束时最多累积 3 条，最后一批最多 4 条，
**任何一问最多跑 7 条工具**。这个 7 是一条断言钉着的，不是注释里的一句说法。

### 验证结果

两处提前跳出**各做了一次反证**，都拿到了红。

★ 更重要的是补上了一条**不变式**：对每一次请求的消息快照逐条检查配对关系，
而不是只加几个「这次跑成了没有」的用例。
用例只能覆盖想得到的场景；**不变式能覆盖想不到的那些** —— 这正是这条缺陷能藏那么久的原因。

## 四、一条检查拦不住东西的时候，会安静地跟着脚本一起消失

### 问题

给「线上演示版」那一态写了一条源码断言，放在检查脚本的靠后位置。

### 现象

做反证时把源码改回「没有保护」的样子，**脚本在更靠前的一节就崩了**。
那条断言所在的整节**压根没被执行到**。

屏幕上看起来只是「脚本炸了」，不是「有一件事坏了」。

### 原因

分两层，**第二层才是关键**：

1. 断言位置在被测代码的**下游** —— 被测对象一坏，后面根本走不到；
2. ★ **更根本的一层**：这个脚本的断言是**记账式**的 ——
   每条失败只塞进一个待汇总的数组，等全部跑完才统一打印。
   所以「红」和「脚本」是**同生共死**的：脚本一崩，之前记下的红也跟着没了。

### 产品判断

严重度中（它不影响用户看到的任何东西），但**它推翻了一个非常自然的第一反应**：

> 「断言没生效？那是它放的位置不对，挪到前面去就行了。」

**实测：挪了，照样没用。**

因为根因不在「断言放在哪」，而在「**断言的结果什么时候被读出来**」。
位置只决定「能不能跑到」，而记账式的汇总决定「跑到了，结果会不会被看见」—— **两层都得对才行**。

★★ 由此得到一条可以带走的规矩：

> **「预检」这个词的全部含义，就是「在还没崩之前把原因说出来」。**
> 所以它天然**不能复用**「先收集、最后汇总」那套机制 ——
> 那套机制的前提是「脚本能活着跑到最后」，
> 而预检要处理的恰恰是**它跑不到最后的那天**。

### 修改

这类检查单独走一条**预检**通道：**当场打印 → 打印完就停 → 输出里带一行明确的汇总**。

### 验证结果

改了两轮才做到。第一版把它挪到脚本最前面，**还是没用** —— 因为记账式汇总的问题没解决；
第二版才改成当场打印并中止。删掉被测的保护之后，预检**当场红并点名原因**。

★ 顺带记一条**不对称**（实测出来的，不是推演）：同一批预检里，各条的**承重程度并不一样**。
其中一条是**唯一的门** —— 它守的保护一旦没了，后面有多处会当场抛异常，脚本立刻完蛋；
另一条**不是** —— 它守的是顺序，顺序写反了不抛不崩，
只是让其中一种状态**静默地、永远地走不到**。

后者比前者更难发现：**前者会喊，后者什么都不说。**

## 五、页面给「变化率 = —」写的理由是假的

### 问题

「数字依据」表的「变化率」一栏显示「—」时，表格下方有一段**无条件渲染**的脚注，
解释为什么是「—」。

### 现象

脚注写的是：

> 变化率为「—」表示**上一周期没有可比数据（分母为 0）**，算不出环比 ——
> 这和「算出来等于 0」是两回事，所以不写成 0%。

**而同一张表里「对比值」那一栏是有数的**（近 30 天窗口 805.1 人/天）。

也就是说：**「上一周期没有可比数据」这句话，与它自己显示的数据直接冲突。**

### 原因

这句话是照着**规则路径**写的 —— 在规则路径下，变化率由本地模板自己算，
产生「—」确实只有那三种情形，所以这个解释成立。

但它**在两条路上都显示**。大模型路径下，这个值是**模型在作答 JSON 里给的**，
模型没给就显示「—」。**页面根本不知道原因** —— 它把「模型没给」当成了「分母为 0」。

### 产品判断

严重度中 —— 它不改变任何数字，但它**当着用户的面把一件假的原因说成真的**。

★ 而这条出现在**最该可信的那张表底下**：
这张表存在的全部意义就是「结论里的每个数字都能找到出处」。
它自己脚底下踩着一句无法支撑的话，比别处更伤。

### 修改

**没有修** —— 这一轮的范围是「验收 / 文档」，功能已经冻结，改了就得重跑全量回归。
位置和原因都已记录在案。

★ **如果将来要修，方向不是改文案**，而是让脚注**知道自己的理由**：
规则路径下说「分母为 0」，大模型路径下说「模型没有给出这个值」——
两条路各自说各自成立的话，或者干脆不说。

### 验证结果

**只记录，不修。** 这是本轮验收中真实发现的三条问题之一，
另外两条见 [`evaluation.md`](./evaluation.md) 的第 4.3 节。

★ 如实说明：验收的五个 CASE **全部 PASS**，这三条**没有一条是功能失败** ——
功能都正常工作，问题在于页面上有一句话不准确。

## 这五条放在一起看

五条里：**一条是真正的功能失败**（第三条），
另外四条全是**「功能跑起来了，但它说了一句不准确或不真实的话」**。

★ 这个分布**不是巧合，是这个项目选的路决定的**：

一个 AI 分析助手最难的不是让它算出数，是**让它别把没算的说成算过了**。
而这一类失败有一个共同的形状 —— **它不报错、不抛异常，
产出的东西通顺、合理、看起来完全正常**。用户读到的是一句自信的话，
只是这句话描述的事情没有发生。

这也是为什么这个项目里防错机制全部是**代码**（数字核对器、窗口一致性检查、
对比对象丢失检查），而不是一句写在提示词里的「请勿编造」——
**一句提示词没有办法被验证，也没有办法知道它什么时候失效。**
