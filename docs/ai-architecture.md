# AI 产品架构

> 这份文档讲的是 **AI 分析助手页**（`/ai`）是怎么设计的：
> 调用链路、工具定义、上下文与状态、可靠性机制，以及系统边界。
>
> 产品层面的决策理由见 [`product-design.md`](./product-design.md)，
> 验证方法与能力边界见 [`evaluation.md`](./evaluation.md)。

---

## 一、一次提问，屏幕上会走过七步

```
① 理解问题 → ② 分析计划 → ③ 选择工具 → ④ 执行分析 → ⑤ 结论 → ⑥ 数字依据 → ⑦ 数据来源
```

这七步是**给用户看的**。它对应的是「一个分析师拿到问题之后会怎么做事」这个心智模型：
先听清问题、再想怎么查、然后动手查、最后给结论并说明依据。

**后台实际上只有两个阶段**：

| 阶段 | 做什么 | 约束 |
|---|---|---|
| **A. 带工具的循环** | 把工具定义交给模型，它自己决定查什么、调几次 | 一批最多 4 条工具调用，**任何一问最多 7 次调用** |
| **B. 强制作答** | 不带任何工具，要求一份结构化 JSON 答案 | 用 `response_format: {type:'json_object'}` |

★ **关于「强制」是怎么实现的**：靠**不给它工具**，不靠 `tool_choice` 参数。
实测 DeepSeek 的思考模式下 `tool_choice: "required"` 会直接返回 400，Kimi 也明确不支持。
**「没给工具」本身就是一种强制**，而且不依赖任何供应商特性。

那 7 次的上限不是拍脑袋定的，是从两阶段结构推出来的硬上限：
上一批结束时最多累积 3 条，最后一批最多 4 条。

## 二、两个工具

模型能调的只有两个工具，都是**本机执行**的：

### `sql_query` —— 在浏览器里的真 SQLite 上跑查询

- 引擎是 sql.js（SQLite 编译成 WebAssembly），跑在浏览器的 Web Worker 里；
- **56 万行全量数据不出这台电脑**；
- 模型现场写 SQL，返回结果里带上列名、前 50 行和总行数。

★ **为什么后端不执行 SQL**：让服务端跑 SQL 就得把整个数据集搬过去，
多花 3–5 秒重建一次数据库，还破坏了「数据不出客户端」这个诚实性论据。
**后端的定位是转发器，不是计算引擎。**

### `python_analysis` —— 调本机真 Python

模型有时需要做它自己算不了的事（变化率、排名、趋势）。这时候它调的是一个**闭集工具**：
任务清单写死在 Python 侧，模型**只能从 5 个任务里选一个 + 指定列名，不能写代码**。

五个任务：百分比变化、排名、均值、趋势、分布。

★ **为什么是闭集**：让模型生成待执行的 Python 代码，等于把任意代码执行的权限交给一个概率模型。
闭集把「模型的能力」和「模型的权限」分开了 —— 它能表达的分析需求足够多，
但**没有一个字的代码是它写的**。

### 工具的 JSON Schema 里没有「时间窗口」参数

这是刻意的。时间窗口是**前端的一等公民**（页面上的 7 / 14 / 30 三个按钮），
工具的 schema 里根本没有这个参数 —— **模型没有权力改它**，只能申报（见第六节）。

理由见 [`product-design.md`](./product-design.md) 的决策一。

## 三、SQL 安全校验：状态机扫描器，不是「先删注释再 grep」

模型写的 SQL 在真正执行之前，必须过一遍校验器。这里有一个**刻意的实现选择**：

**没有**采用「先删掉注释、再用关键词匹配」这种常见做法。原因是那样做会产生**两份字符串** ——
校验器看到的那份，和 SQLite 实际执行的那份。两份一旦分叉，后果是**放行删表**。

所以校验器是一个**状态机扫描器**：它自己按字符扫描整条 SQL，理解引号、注释、字符串字面量的边界，
在扫描过程中判断语句结构和禁用词。

★ **一个具体的例子说明为什么「只看开头」不够**：SQLite 允许在 CTE 里写 DML ——

```sql
WITH x AS (DELETE FROM video_views RETURNING *) SELECT * FROM x
```

这条语句的首 token 是 `WITH`，只看开头会**整个放行**。
而它长得和本项目的正常 CTE 几乎一样，人不盯着看根本分不出来。
所以禁用词查的是**任意位置**，不是只看第一个词。

## 四、上下文与状态

### 4.1 会话层：上下文由模型自报，前端只做机械合并

多轮对话需要记住「上一轮在分析谁、跑的是几天、和谁比」。这个信息的来源有一个刻意的选择：

**由模型在阶段 B 的作答 JSON 里自报**（一个 `context` 字段），前端只做机械合并。

★ 为什么不自己从用户的提问里猜：那需要在前端按问题内容做分支判断 ——
「这句话里有『他们』就继承上一轮的人群」这类规则一旦写下去，
就变成了**第二个真相来源**，而且它错的时候不会报错。

★ 这个选择还有一个直接好处：**整个会话层架在现有两阶段之上，没有新增任何一次请求。**
一次提问仍然是 3 次模型请求，多轮对话没有让它变贵。

### 4.2 历史只带最近 3 轮

带上全部历史意味着每条问题都更贵。代价是明确的：问到第 5 轮时，
第 1 轮建立的指代会失效。**页面会如实说明这一点，但接不住。**

### 4.3 上下文卡片：每个字段标出来源

界面上有一张卡片显示「这一轮在分析什么」，每个字段后面标着它的来源：

- **模型申报的** —— 这一轮模型新给出的；
- **从上一轮继承的** —— 会话层合并进来的；
- **来自当前窗口** —— 由页面上的按钮决定，不是模型说的。

用户随时能看到「这一轮到底在分析什么」，不用自己回忆前几轮说过什么。

## 五、可靠性设计：三层「别胡说」机制

**全部是代码，不是提示词。**

| 机制 | 拦什么 | 判据 |
|---|---|---|
| **数字核对器** | 结论里出现找不到出处的数字 | 结论里的每一个数字，都要能在**工具返回的结果**里找到出处；找不到的**原样列成红色标签** |
| **时间窗口一致性检查** | 模型嘴上说的窗口和真正跑的窗口对不上 | **刻意取松**：正文里只要提到过真实窗口**一次**就不报警 |
| **对比对象丢失检查** | 多轮追问里主对象或对比对象被覆盖 | 两个方向都拦：「有对比对象、主对象没了」和「主对象还在、对比对象没了」 |

关于数字核对器，有两件事必须说清楚：

1. **它不替你判断模型是不是在编。** 它只做一件事：把这个数字拿去工具结果里找。
   找不到就列出来，由人去看结果表。**「找不到出处」不等于「是编的」** ——
   也可能是模型自己对结果做了换算（比如把秒换算成分钟），那种情况下数值可能是对的。
2. **它抓的是「过程不合规」，不总是「结果错误」。** 提示词里明令禁止模型自己心算，
   要求它调用 Python 工具。模型如果直接手算了一个正确的数写进结论，核对器照样会列出来 ——
   因为「这个值不是工具直接返回的原值」。**这是它该做的事，不是误报。**

★ **关于窗口一致性检查为什么取松**：模型经常写「近 30 天里的最后 7 天」这种完全正常的句子。
判紧了全是假告警，而**假告警比不检查更糟** —— 核对器一旦开始乱叫，
用户就再也不信它，包括它真正成立的那几次。

## 六、意图与执行解耦

这是整个 AI 层最核心的一条设计。

整条链路里「时间窗口」只有一种一等公民 —— 页面上的那三个按钮。
**模型能做的只有一件事：在这一轮的作答 JSON 里申报一个它想要的天数。**
前端读到之后**只拨按钮，绝不自动重跑**。

**结果卡片上的「时间范围」永远来自这一轮真正执行的参数**，不是模型在正文里说的那个数。

界面上还有一条横幅负责把两者的落差说清楚。★ 这条横幅有**两种措辞，绝对不能混**：

- 用户**自己**拨的按钮 → 「**你把**时间窗口切成了…」
- 模型申报后**替他**拨的 → 「**模型把**时间窗口理解成了…」

**混了就是一句假话** —— 页面对用户自己做的操作，会说成是模型做的。
这不是假设出来的风险，它真的发生过，见 [`bad-cases.md`](./bad-cases.md) 的第一条。

★ 由此得到一条通用规则：**凡是决定「屏幕上显示哪一句」的条件，都要能被单独钉住。**
`a && b && c` 这种内联条件是最容易被人「简化」掉、并且简化之后**所有检查都还是绿的**的地方。

## 七、系统边界

### 7.1 什么出了网

| 什么 | 出网吗 |
|---|---|
| 全量数据集（56 万行） | ❌ 不出。SQL 在浏览器里跑 |
| 某一次查询的结果（列名 + 前 50 行 + 总行数） | ✅ **出网**，作为工具返回值回传给模型 |
| 用户的问题原文、上一轮的分析上下文 | ✅ 出网 |

★ **第二行是工具调用的固有含义，省不掉** —— 模型不看结果就没法决定下一步。
页面上已经如实写明这一条，而不是含糊带过。

### 7.2 为什么管理 API Key 的服务不上公网

AI 分析助手页有**两条并存的路径**：

| 路径 | 问题理解 / 写结论 | 执行 SQL | 需要什么 |
|---|---|---|---|
| **大模型路径** | ✅ 真调 DeepSeek API | ✅ 真跑 | 一个跑在**本机**的 Node 服务，用来保管 API Key |
| **规则路径**（降级方案） | 本地关键词规则 + 模板填真实数字 | ✅ 真跑（同一套引擎） | 不需要任何服务 |

Live Demo 部署在静态托管上，**背后刻意没有后端**。所以线上那一页走的是规则路径。

**为什么那个服务不能放到网上**：API Key 一旦跟着网站部署到公网，
任何人都能拿它刷爆账号额度，而账单算在作者头上。
**这是设计，不是故障** —— 页面横幅会如实写明当前走的是哪条路径、以及为什么。

★ 这一条在 README 和页面上都必须讲清楚。否则面试官点开 Live Demo 看到 AI 页走规则路径，
第一反应会是「部署坏了」，而不是「这是一个有意的架构选择」。

### 7.3 后端有多薄

全项目唯一的服务端进程是**本机**的（`server/`，零新增依赖，只用 Node 内置模块），
只做两件事：把请求转发给大模型、把某一次查询的结果交给本机 Python 算。

它**不持有全量数据**，也**不执行 SQL**。

★ **不启动它，所有页面照旧全部能用。** 只有 AI 页会如实降级成规则路径，
并把原因显示出来 —— 用户在**看到任何结论之前**就知道走的是哪条路。

### 7.4 探测失败可以自动降级，跑到一半失败绝不自动降级

启动时探测一次后端健康状态，探不到就如实说明原因、走规则路径。

但已经调了两次工具、第三次请求超时的时候，**绝不悄悄换成模板** ——
那会让用户看到一份「看起来像模型给的、其实是本地模板给的」答案。
**这是最坏的一种失败**：它不报错，只是让人把来源读错。

## 八、几条实现约定

这几条看起来是工程细节，但每一条都对应一个具体的产品后果。

**① 系统提示词必须在前端拼。**
提示词里要用到真实的库表结构、年龄段定义、分区表。这些必须用前端已有的那份源数据现场生成，
**不能在后端再抄一份** —— 抄一份就是两个真相来源，改一处漏一处**不会报错**。

**② 模板从「写结论」降级成「取值器」。**
规则路径有一套结论文案模板。在大模型路径下，这套模板**只负责从模型给的答案里取值，不生成任何文字**。
如果模板和模型各写一份结论，说法打架时不报错，只会让人不再信任这一页。

**③ 规则路径原封不动地保留成了降级方案。**
新增 LLM 路径没有改动规则路径，两条路并存、互不干扰。

**④ 探针返回四种状态。**
`ready`（本机后端在）/ `rule`（后端不在，走规则路径）/ `static`（静态打开，比如本地双击 `file://`）/
`deployed`（**不是本机地址** —— 背后一定没有后端，因为那个服务刻意不上公网）。
第四种是专门为线上演示加的：它让页面能说「这是线上演示版，AI 页走的是规则路径」，
而不是说「本机后端连不上」—— 后者在线上是一句让人以为部署坏了的假话。
