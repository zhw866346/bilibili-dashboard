# 验证方法与能力边界

> 这份文档讲三件事：**怎么验证的**（方法）、**验证了什么**（验收清单与结果）、
> **没验证什么 / 做不到什么**（能力边界）。
>
> 五个真实 Bad Case 的完整记录见 [`bad-cases.md`](./bad-cases.md)。

---

## 一、评估方法

### 1.1 四层验收 —— 不许合并成一句「测试全部通过」

一个 AI 分析功能，从代码到用户看到的东西要经过四层。每一层验的是**完全不同**的东西，
任何一层绿了都不能推出另一层也绿：

| 层 | 验的是什么 | 结果 |
|---|---|---|
| **A. 自动化检查** | 纯函数、会话继承、历史裁剪、SQL 安全校验、数据对账、页面渲染 | ✅ 已验证 |
| **B. 假模型跑通全链路** | 两阶段循环、工具调用、消息配对、窗口申报的**管道** | ✅ 已验证 |
| **C. 真实 LLM** | 真模型会不会**真的**按约定的契约作答 | ✅ 已验证 |
| **D. 浏览器 UI** | 按钮真的会跳吗、横幅真的会出现吗、图表真的画出来了吗 | ✅ 已验证 |

★ **C 层为什么是承重的**：自动化检查和假模型都只能证明「如果模型按约定作答，系统会正确处理」。
它们**证不了模型到底会不会按约定作答** —— 真模型完全可能压根不申报那个字段（那时它是 `null`，
整个「最近 7 天呢」的功能静默失效，而**页面上不会有任何报错**）。
这件事只有真人拿真 key 跑一遍才知道。

★ **D 层为什么不能省**：按钮会不会跳、横幅用哪一句措辞、图表有没有画出来，
这些在 A / B / C 三层里**全都看不到** —— 它们不渲染页面。

### 1.2 反证：每一条断言都要能被推翻一次

这个项目有一条贯穿始终的规矩：

> **每一条新写的检查，都要把源码改回「没有这个保护」的样子，确认它真的会红，再改回来。**

理由很直接：一条永远不会红的检查，比没有检查更糟 —— 它看上去像是有东西在守着。

反证做过之后，暴露出来的问题几乎全在「检查本身」这一侧，而不是「被检查的代码」这一侧。
举三个真实例子（完整记录见 [`bad-cases.md`](./bad-cases.md)）：

- 用「值相等」写的断言，**分辨不出这个值是算出来的还是手抄的** ——
  两条路今天产生同一个值，断言就永远发现不了分叉；
- 用「导入进来的常量」去比页面上渲染出来的文字 —— 反证时会把常量一起改坏，
  于是期望值和实际值同时变，断言**永远是绿的**；
- 一条检查拦不住东西的时候，**它会安静地跟着脚本一起消失** ——
  脚本崩在更靠前的一节，那条检查连报错的机会都没有。

### 1.3 怎么记录一次失败

每一个发现都按同一组字段记录，缺一条就不算记完：

| 字段 | 含义 |
|---|---|
| **Case** | 一句话说清是什么问题 |
| **触发操作** | 用户说了什么 / 点了什么 |
| **预期** | 本来应该发生什么 |
| **实际** | **实际**发生了什么（抄页面原话，不转述） |
| **失败类型** | 功能失败 / 静默错误 / 假告警 / 假话 / 检查失效 |
| **严重度** | 见下 |
| **根因** | 为什么会出现 |
| **当前处置** | 现在怎么防住它 |
| **状态** | 已修复 / 已加固 / 只记录不修 |

**严重度只有一条判据：它会不会让看的人得出错误结论。**

| 档 | 判据 |
|---|---|
| **高** | 会让人读错结论 —— 哪怕只是少一个数 |
| **中** | 不会读错，但会让人不再信任这个页面 |
| **低** | 只是不好看、多一次点击 |

★ **一条红线：禁止把「理论风险」写成 Bad Case。**
「我觉得这里可能会出问题」不是 Bad Case，「我跑了一遍，它真的这么错了」才是。
没有证据的只能进第七节的能力边界，并且必须写明「为什么它不能算 Bad Case」。

## 二、五个 CASE 的验收设计

这一节是这套方法里最具体、也最可复用的部分：**每一问都写清了「要看的」「应该是什么样」
和「失败时屏幕上是什么样」**。

> ★ 下面这份清单的用途不只是「验收一次」。它同时是**将来改动 AI 路径之后的操作手册** ——
> 「失败时屏幕上是什么样」那一栏，每一条现在仍然成立。

### 前置条件（不满足的话整张单子白测）

1. 必须启动**本机后端**，否则整页走规则路径，下面全是**大模型路径**的东西，一样都看不到。
2. `server/.env` 里的 API Key 还有余额。
3. 每开一个新 CASE 先点「新建分析」清空上下文，否则上一轮的上下文会串进来。
4. 第一问跑完后，按钮应该写「**重新分析**」。如果它写的是「用大模型重新跑一遍」，
   说明第一问走的是规则路径 —— 先别往下做，回去查后端。

### CASE 1 · 「最近 7 天呢」

> 「哪个年龄段 DAU 最高？」→ 等它答完 →「最近 7 天呢？」

| # | 要看的 | ✅ 应该是什么样 | ❌ 失败时屏幕上是什么样 |
|---|---|---|---|
| 1 | 模型是否正确申报了 7 天 | **只能间接判断**（这个值界面不显示）—— 看第 2 条 | —— |
| 2 | 时间窗口按钮是否**自动切到「近 7 天」** | 按钮高亮跳到「近 7 天」 | 按钮**停在「近 30 天」没动** |
| 3 | 旧结果是否**仍如实显示原时间范围** | 结果卡片上「时间范围」**仍然写着近 30 天** | 卡片跟着变成「近 7 天」→ **这是最严重的一种失败**：系统在假装跑过 |
| 4 | 是否出现「需要重新分析」的提示 | 出现横幅，并说明「按钮已经拨过去了，但下面这份结果还是近 30 天的」 | 按钮跳了但**没有任何提示** → 用户会以为下面就是 7 天的数据 |
| 5 | 点「重新分析」后新结果**真的**用 7 天数据 | 卡片变成「近 7 天」；**结论里的数字和第一问不一样** | 卡片还是 30 天，或数字**和第一问一模一样** → 没真的重查 |

### CASE 2 · 「最近 14 天呢」

同 CASE 1，把追问换成「**最近 14 天呢？**」，五条照查一遍。
这一条验的是**完整链路**，不靠自动化检查的推理。

### CASE 3 · 「最近 30 天呢」（当前本来就是 30 天）

| # | 要看的 | ✅ 应该是什么样 | ❌ 失败时屏幕上是什么样 |
|---|---|---|---|
| 1 | **不许**出现「模型切换了时间窗口」的提示 | 没有那条横幅（因为窗口**根本没变**） | 出现「模型把时间窗口理解成了近 30 天…」→ 一句无中生有的提示 |
| 2 | **不许**有无意义的窗口切换 | 按钮动都没动 | 按钮闪了一下 |
| 3 | 分析状态保持一致 | 上下文卡片、结果卡片都还是原来那份 | 结果被清空 / 卡片少了一行 |

> ⚠️ **这一条的局限必须如实说**：它「通过」和「模型压根没申报」
> **在界面上长得一模一样**（都是什么都不发生）。
> 所以它只能证明「没有出现假提示」，**不能证明「模型正确申报了 30」**。
> 这一条最终是靠打开开发者工具看网络响应才区分开的。

### CASE 4 · 「和 25-31 相比呢」

> 「哪个年龄段 DAU 最高？」→ 等它答完 →「和 25-31 相比呢？」

| # | 要看的 | ✅ 应该是什么样 | ❌ 失败时屏幕上是什么样 |
|---|---|---|---|
| 1 | 主分析对象**仍在** | 上下文卡片上「用户群体 18-24」**还在** | 那一行**没了** → 被覆盖了 |
| 2 | 对比对象**新增而不是覆盖** | 卡片上**同时**有「用户群体 18-24」+「对比对象 25-31」**两行** | 只有一行 |
| 3 | 最终回答**真的做了比较** | 结论里**两个年龄段的数据都出现**了 | 只讲 25-31、或只讲 18-24 → 答非所问 |
| 4 | 工具轨迹与最终结论**一致** | 展开「分析路径」，查到的东西和结论对得上 | 结论里出现工具结果里**找不到出处的数字** |

### CASE 5 · 连续三问（三个维度同时保持）

> 「哪个年龄段 DAU 最高？」→「和 25-31 相比呢？」→「最近 7 天呢？」

上下文里**主分析对象 / 对比对象 / 时间窗口三者是否同时正确**：
用户群体 18-24、对比对象 25-31、时间窗口近 7 天。

★ 这一条是最难的：前两问建立了「比较」这个维度，第三问又要加「窗口」这个维度。
**三个格子任何一个空了或者串了，就是失败。**

### 验收结果

**五个 CASE 全部 PASS。** 最硬的一条证据是 CASE 3 ——
在开发者工具的网络响应里搜到了模型申报的字段，把「模型说了 30」和「模型什么都没说」区分开了。
其余四个 CASE 也都拿到了对应的界面证据（按钮真的跳、横幅两种措辞都亲眼看到、
上下文卡片两行并存、结果卡始终写本次真正跑的窗口）。

## 三、验证覆盖了什么

自动化检查覆盖的是「机器能看的那一半」。按检查对象分，大致是七块：

| 检查对象 | 拦的是哪一类失败 |
|---|---|
| **数据层对账** | Python 算的数和前端算的数是**两套独立实现的同一批口径**。没有机制保证它们一致，只能靠一遍遍地对 |
| **页面数据通路** | 每个页面拿到的数据形状对不对、有没有缺字段 |
| **页面渲染** | 七个页面各渲染一遍，查白屏和 `undefined` / `NaN` 这类脏字符 |
| **规则路径** | 意图匹配错了、结论文案漏分支、引用了不存在的案例、手写的 SQL 跑不通 |
| **大模型路径** | 用假模型按序吐预设响应，验完整的两阶段循环（**不联网、不花钱**） |
| **真 Python 端到端** | 真 spawn 本机 Python、真起后端走 HTTP、真 SQLite 算真数据 |
| **SQL 安全校验** | 先证明漏洞是真的（真的执行一条删表 SQL 看它发生了什么），再证明拦住了 |

★ 这些检查跑在本机开发环境里，**不随仓库发布**。
所以它们的存在本身就是一句「无法核实的话」——
这也是为什么这份文档里**不列检查的条数**：一个读者无法核实的精确数字，
比一个粗糙但能自己验证的说法危险得多。

**读者自己能核实的**是第二节那五个 CASE 的判据 —— 照着清单在页面上逐条看一遍就行。

## 四、能力边界

> 下面每一条都是**如实列的**，不是「将来会做」。
> 它们要么是主动划出的范围，要么是有意的取舍。

### 4.1 数据层面（这一条最需要主动说）

1. **数据全部是模拟的，而且数据里的「规律」是设定出来的，不是发现的。**
   由固定随机种子程序生成，与哔哩哔哩的真实经营数据毫无关系。
   所以这些图表能证明的是「分析链路是通的」，不能作为任何真实业务判断的依据。
   完整说明见 [`product-design.md`](./product-design.md) 4.3 节。

### 4.2 有意的设计取舍

2. **不支持任意日期区间。** 「和 8/25–8/31 相比呢」接不住，只能做等长窗口比较（7 / 14 / 30）。
   这是**主动划的范围边界**，不是做不到。
3. **历史只带最近 3 轮。** 带上全部历史意味着每条问题都更贵。
   代价明确：问到第 5 轮时，第 1 轮建立的指代会失效 —— **页面会如实说明，但接不住**。
4. **查询结果的前 50 行会发给模型公司。** 这是工具调用的固有含义，省不掉。
   全量数据不出本机，但**模型实际看到的那几十行确实出了网**，页面上已如实写明。
5. **时间窗口一致性检查刻意取松。** 判紧了会全是假告警，而**假告警比不检查更糟**。
   代价是：正文通篇说近 7 天、但碰巧对了一处「近 30 天」时不会报警。
   这是**刻意选的那一侧**，不是没想到。
6. **SQL 安全校验不限制日期范围。** 那条限制拦的是「说漏嘴」，不是「不许查」。
   模型仍然可以自己写死一段日期去查别的区间 —— 那是**能力**，不是**越权**。

### 4.3 已知的缺口（记录在案，未修）

7. **模型申报的时间窗口值，在界面上从来没有被渲染过。**
   页面只在两处读它（拨按钮 / 选横幅），没有一处把它显示出来。
   后果：验收清单里「模型是否正确申报」**只能靠按钮跳没跳间接判断**。
   ★ 不补 UI 的原因：补它属于新增功能，与功能冻结冲突。**这是一个已知的可观测性缺口。**
8. **数字核对器的白名单是手工维护的，会有缺口。**
   它只认得口径卡片里教给模型的常数的某几种写法。模型换一种写法（比如把 `0.8` 写成 `80%`）
   就会被误标成「没找到出处」—— 这是**假告警，不是漏报**，数值本身是对的。
   ★ 正确的修法不是「把漏掉的常数加进白名单」（那是打补丁，下次换第三种写法还会漏），
   而是**让白名单从口径卡片派生**：卡片教了哪些常数，白名单就该认识哪些。
9. **「变化率为 —」的脚注理由，在大模型路径下是假的。**
   那句话是照着规则路径写的（那里只有三处会产生 `—`），却在两条路上都显示。
   大模型路径下这个值是模型给的，模型没给就显示 `—`，**页面根本不知道原因**，
   却把它当成了「上一周期没有可比数据」。完整记录见 [`bad-cases.md`](./bad-cases.md)。

### 4.4 一条未能定性的观察

10. **一次核对器报出的数字，查不出它从哪来。**
    把数据集里几百个真值候选全算了一遍，**一个都对不上**。
    ★ 按本项目的红线，**猜「它大概是模型编的」是不允许的** ——
    那正是把理论风险写成事实。所以它**不算 Bad Case**，只作为一条观察记在这里：
    **未能复现、未能定性。**

### 4.5 主动没做的能力

11. **没有自动下钻、没有长期记忆、不引 RAG / MCP / Multi-Agent、
    没有「事实 / 判断 / 假设 / 建议」四段分离。**
    这一页能连着聊、能接窗口与比较追问，但**不能自己往下钻一层**。
    这是**主动划出的 MVP 范围**，理由见 [`product-design.md`](./product-design.md) 的决策四。

### 4.6 定位层面

12. **这是一个个人 MVP，不是生产系统。**
    没有鉴权、没有并发设计、没有监控告警，持 API Key 的服务刻意只绑本机。
    它是**作品集 Demo**，不应该按生产系统的标准来读。

## 五、还可以说的和不能说的

### ✅ 可以说的

- 「**模拟**内容平台数据」/「自造数据集」
- 「真实 **LLM API** 调用」/「真实 **Tool Calling**」
- 「**个人** MVP」/「作品集项目」
- 「**AI 辅助**开发」
- 「做了数字核对 / 窗口一致性 / 对比丢失三层机制，用来**减少**模型编数字」

### ❌ 不可以说的

| 不能说 | 为什么 |
|---|---|
| 「B 站内部真实数据」/「B 站真实 DAU」 | **数据是模拟的**。这是最严重的一条 |
| 「生产级」/「企业级」 | 它是个人 MVP，没有鉴权、没有并发设计、没有监控 |
| 「**完全**可靠」/「**完全**消除幻觉」 | 核对器只能标出「找不到出处」，**不能判断对不对** |
| 「真实效率提升 XX%」 | 没有一个真实业务跑过它，**这个数不存在** |
| 「接入了 B 站的 XX 能力」 | 没有任何内部接口 |

★ **为什么这条线划得这么重**：这是求职作品。把模拟数据包装成真实数据，
一旦被面试官问穿，**比不做这个项目还糟**。
反过来，**主动说清「数据是模拟的、规律是设定出来的、哪一层是真的」**，
本身就是数据产品岗该有的判断力。
