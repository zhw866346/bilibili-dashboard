## 一、项目背景

一个面向**数据分析 / 商业分析 / 数据产品 / AI 产品**岗位的个人作品集项目。

业务场景设定为「一个视频社区的用户活跃度与内容消费」。选这个场景的理由是它的分析链路足够长：
用户规模 → 活跃 → 内容消费 → 互动 → 分区差异，每一层都能拆出可量化的指标，
足以撑起一套完整的分析框架；同时它又是一个人人都能理解的业务，不需要额外解释背景。

**数据是自造的模拟数据集**（见第四节）。这一点在文档最前面就说清楚，因为它是理解后面所有内容的前提。

---

## 二、问题定义

这个场景下，业务方真正会问的问题可以归成四类：

| # | 问题 | 谁来回答 |
|---|---|---|
| 1 | 大盘怎么样了？ | 首页概览 |
| 2 | 谁在活跃、谁在流失？ | 用户分析 |
| 3 | 什么样的内容在起作用？ | 内容分析 / 用户 × 内容 |
| 4 | **不懂 SQL 的人，能不能用自然语言把这些问出来，并且相信得到的答案？** | AI 分析助手 |

前三类是这个场景的常规分析需求，对应 7 个图表页。

**第四类才是这个项目的重点。** 把数据算对不难，难的是「让一个不能看 SQL 的人相信屏幕上那句话」。
大模型最容易犯的错不是算错，而是**把没算的说成算过了** —— 一个看起来很确定的结论，
背后可能压根没有查询支撑，或者查的是另一个时间窗口。用户看不出来，因为错的那份长得和对的一模一样。

所以第 4 类问题实际上包含两个子问题：

- **能不能问得动？** 自然语言 → 数据查询 → 结论，这条链路要通；
- **能不能信？** 结论里的每个数字、每个时间范围、每次多轮追问的上下文，都要能被追溯和核对。

第二个子问题决定了这个项目大部分的设计工作。

## 三、产品目标

1. **走通一条完整的分析链路。**
   定义业务问题 → 搭建指标体系 → 取数 → 分析 → 可视化 → 输出业务判断。
   每一环都留下可复现的痕迹：口径写在代码里、SQL 现场真跑、Python 真跑、结论有数据支撑。

2. **把「防 AI 胡说」做成机制，而不是做成一句提示词。**
   写一句「请勿编造数据」是成本最低、也最没有用的做法 —— 它不可验证，也无法知道什么时候失效。
   这个项目里的防错机制全部是**代码**：数字核对器、时间窗口一致性检查、对比对象丢失检查。
   它们会在模型的输出**不符合约定时**明确指出，而不是相信模型的自述。

3. **全程如实说明边界。**
   哪些是真的、哪些是模拟的、哪些是刻意没做的、哪些做了但不保证 —— 全部写在明面上。
   这是求职作品，把模拟数据包装成真实数据，一旦被问穿，比不做这个项目还糟。

## 四、分析框架

### 4.1 指标体系

按「规模 → 活跃 → 消费 → 互动」四层组织：

| 层 | 指标 |
|---|---|
| 用户规模 | DAU、各年龄段用户规模 |
| 活跃度 | 活跃率、人均观看时长、单次观看时长 |
| 内容消费 | 播放量、独立观看用户数、观看完成率（观看时长 ≥ 视频总时长的 80% 算完成） |
| 互动 | 点赞率、投币率、收藏率、弹幕率、评论率 |

**两条口径纪律**（都是真实踩过坑之后写进代码的）：

1. **播放量可以按天相加，独立观看用户数不行。** 前者是累积量，跨天求和没问题；
   后者必须先按人去重再数。这两个混用会让数字虚高，而且**虚高得看起来很合理**，一眼看不出来。
2. **「人均观看时长」有两个分母。** `总时长 ÷ 独立观看用户数` 是人均，
   `总时长 ÷ 播放次数` 是单次 —— 两个数差一个量级，项目里反复强调不能混用。
   SQL 案例里专门有一个案例演示这两者的区别。

### 4.2 数据分层

```
dataset.ts（造明细） → metrics.ts（算口径） → selectors.ts（拼页面要的形状） → 页面
```

页面组件只负责「怎么画」，不负责「怎么算」。任何一个数字对不上，都能顺着这三层找出来。
加新指标时不绕过这一层。

这么分的直接好处是：**将来接入真实数据源，只需要替换第一层，7 个页面的代码一行都不用改。**

### 4.3 数据来源与诚实性设计

- 由固定随机种子（`SEED = 20260910`）程序生成；
- 规模：**6,000 名用户 / 1,000 个视频 / 60 天 / 565,740 条观看记录**，截止 `2026-09-10`；
- **与哔哩哔哩（B 站）的真实经营数据毫无关系**，不来自任何内部渠道，也不是抓取结果；
- 固定种子意味着任何人重新运行都会得到完全相同的数字，便于核对。

★ **比「数据是模拟的」更要紧的一句：数据里的「规律」是设定出来的，不是发现的。**

页面上每一条「规律」——「年轻人更活跃」「某个年龄段偏爱某个分区」——
都是生成数据时先设定好参数、再让数据体现出来的。
所以这些图表能证明的是**「分析链路是通的」**：口径怎么定、去重怎么做、交叉分析怎么关联、
指标怎么从明细逐条算出来。它**不能**证明「真实用户是这样的」，也不能作为任何真实业务判断的依据。

**页面上守这条线的两处设计**：

- 每个页面顶部常驻一条模拟数据提示；
- 首页概览和用户分析两页的最下方有一块**「这份数据是怎么来的」**，
  里面那张对照表逐条列出「页面上的哪个差异 ←→ 代码里的哪个参数 ←→ 设的值是什么」。
  表里的数值是**直接从生成参数里读出来的**，不是手抄 —— 改了参数表会跟着变，
  不会出现「说明和数据对不上」这种情况。

## 五、功能设计

### 5.1 七个页面

| # | 页面 | 内容 |
|---|---|---|
| 1 | 首页概览 | 大盘核心指标：DAU、人均观看时长、人均观看视频数、互动率；DAU 趋势、年龄分布、分区表现 |
| 2 | 用户分析 | 各年龄段用户规模 / 活跃率 / 人均观看时长与条数；年龄 × 内容偏好热力图 |
| 3 | 内容分析 | 八个分区的播放量 / 独立观看用户 / 人均观看时长 / 完播率 / 四种互动率；内容表现矩阵；13 列可排序明细表 |
| 4 | 用户 × 内容 | 交叉分析：4 项交叉指标、年龄 × 内容偏好热力图、各年龄段 TOP3 内容、内容用户结构、消费深度、互动行为、机会矩阵、32 行交叉明细表 |
| 5 | SQL 分析 | 9 个在浏览器里**真实执行**的 SQL 案例（含 CTE 与窗口函数）；每条按「业务问题 → 使用字段 → SQL → 查询结果 → 分析解释 → 业务意义」展开 |
| 6 | Python 分析 | 离线跑**真 Pandas**的 11 个分析模块 + 逐项对账；附分析脚本源码与「结果还配得上当前数据吗」的陈旧检查 |
| 7 | **AI 分析助手** | 自然语言提问 → 真调大模型 → 模型自己写 SQL → 真跑 → 写结论。**本项目的核心**，设计见 [`ai-architecture.md`](./ai-architecture.md) |

### 5.2 可视化上的三个选择

**① 用二维矩阵代替排名表。**
内容分析页如果只给每个分区排个名，看不出「流量大但没人看完」这类结构性问题。
所以把「流量规模」和「消费深度」放成两个轴做四象限气泡图 —— 同一个分区在两个轴上位置不同，
才暴露出它真正的问题在哪。用户 × 内容页的机会矩阵是同一个思路。

**② 配色经过色盲安全校验，并且颜色不单独承载信息。**
八个内容分区使用固定色位（游戏恒为蓝、知识恒为橙），翻到哪一页都认得出；
对比度偏低的颜色一律在图形上**直接标注数值**；每张图都提供**表格视图**，
保证任何人在任何情况下都能读到准确数字。有序分类（如年龄段）用「浅 → 深」递进色阶，
而不是一堆互不相干的颜色。

**③ 每张图配一句「怎么读」，而不是只给图例。**
图例解决「这条线是什么」，不解决「这个形状意味着什么」。后者才是业务方真正需要的信息。

## 六、核心产品决策

> 这一节是这份文档最值得讲的部分 —— 它记的是**为什么这么做**，而不是**做了什么**。

### 决策一：意图与执行分开 —— 模型可以改变建议，不能改变事实

**场景**：用户已经看过一份「近 30 天」的分析结果，然后在输入框里追问一句「最近 7 天呢」。

**做法**：
模型负责**理解意图**，在作答里申报一个它认为用户想要的天数（7 / 14 / 30）。
前端读到之后，**做且只做一件事：把页面上的时间窗口按钮拨过去**。
它**绝不自动重跑**。屏幕上会出现一条横幅，如实说明三件事：

> 模型把时间窗口理解成了「近 7 天」，按钮已经替你拨过去了 ——
> 但下面这份结果还是「近 30 天」的，它并不会因为按钮动了就变成新窗口的数据。
> 换窗口要重新查一遍数据库，所以不自动重跑。点一下「重新分析」即可。

**结果卡片上的「时间范围」永远写着那一轮真正跑的天数**，按钮被拨过去之后它不会跟着变。
这是整条设计里最要紧的一格。

**为什么**：自动重跑看上去只省一次点击，代价却是四样 ——
调用成本翻倍（一次提问从 3 次请求变 6 次）、用户要多等十几秒、
屏幕上会先闪一份旧窗口的答案再被盖掉、以及用户分不清刚才看到的是哪个窗口的结果。

★ **一句话：「按钮变了」不等于「数据查过了」，这个区别必须让用户看得见。**

### 决策二：比较是「新增一个维度」，不是「覆盖当前对象」

**场景**：上一轮在分析「18-24 岁」，用户追问「和 25-31 相比呢」。

**做法**：上下文里**同时**保存主分析对象和对比对象两个独立的格子。
界面上「用户群体 18-24」和「对比对象 25-31」是**两行**，各记各的。

**为什么**：「和 X 相比」的语义是「当前对象 **VS** X」，不是「把当前对象换成 X」。
这是多轮对话里最容易被悄悄搞坏的一件事 —— 用户以为自己在「再加一个维度」，
系统却在「换一个对象」，而**两种情况的界面看起来一模一样**，不报错、不抛异常，
只是答非所问。

**机器侧两个方向都拦**：「有对比对象、主对象没了」会报，「主对象还在、对比对象没了」也会报。
两半合起来才拦得住。

### 决策三：系统状态优先于模型叙述

**问题**：模型能理解和描述分析过程，但它的自然语言**不是可靠的系统状态来源**。
它可能说了一个没跑过的窗口，可能把「我打算按 7 天分析」说成「我按 7 天分析了」，
也可能压根不提窗口，让用户自己猜。

**做法**：当模型说的话和系统的状态冲突时，**以系统状态为准，并且把冲突显示出来** ——
不是去「调和」它，更不是让模型的话覆盖掉系统状态。

具体到实现上，三样防错机制都是**独立的代码在检查模型的输出**，而不是让模型自检：

- 结论里的每一个数字，都要能在工具返回的结果里找到出处，找不到的列出来；
- 正文通篇说的时间范围，和这一轮真正跑的对不上时报警；
- 主分析对象 / 对比对象任一丢失时报出来。

**为什么**：让模型自检，等于让被检查的人自己写检查报告。它今天说「我核过了」，
明天还是可能漏 —— 而**这一页最不能出的错就是「看起来核过了」**。

★ 这条决策要防的是最坏的一种失败：**模型说了什么，系统就假装执行了什么。**

### 决策四：功能在这一版停下的理由

这是**主动的范围控制**，不是「做不下去了」。

- **已经具备**：多轮上下文分析、时间窗口追问、比较型追问、SQL 与 Python 的 Tool Calling；
- **刻意没做**：自动下钻分析、长期记忆、RAG / MCP / Multi-Agent、任意日期区间、
  「事实 / 分析判断 / 业务假设 / 建议」四段分离。

**理由**：这些不是验证当前核心产品假设所必需的能力。
这个产品的核心假设是「**用户愿不愿意用自然语言连着追问、系统能不能诚实地回答**」——
现有版本已经足以验证它。再往下做（自动下钻、长期记忆）属于**换一个假设**，
应该先拿到真实用户反馈再决定做不做，而不是先写代码。

★ 换个说法：**在没有真实用户反馈之前，继续加功能只会让「不知道做给谁」这件事变得更贵。**
